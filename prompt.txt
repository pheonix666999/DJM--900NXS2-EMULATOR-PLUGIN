PROJECT WORKING NAME
QuadBeat FX

PRODUCT
A professional standalone four-channel DJ mixer and Beat FX desktop application for:

- Windows 10/11 x64
- macOS 12 or newer
- Apple Silicon and Intel Macs

The application is functionally inspired by professional four-channel club mixers, including the DJM-900NXS2 effects workflow, but it must use completely original branding and original graphical styling.

DSP BEHAVIOR

Delay:
- beat-synchronized delay time,
- controlled feedback where applicable,
- smooth time changes.

Echo:
- repeated feedback echo,
- tempo synchronization,
- safe feedback limit.

Ping Pong:
- alternating stereo repeats,
- stable feedback,
- correct mono-input handling.

Spiral:
- feedback delay network with evolving pitch/phase or spectral movement,
- create a distinctive spiralling behavior,
- document the chosen approximation,
- do not leave it as an alias of another effect.

Reverb:
- stereo reverb,
- tempo division influences decay or predelay,
- TIME controls the primary duration-related parameter.

Trans:
- tempo-synchronized rhythmic gating,
- click-free transitions,
- division controls gate rhythm.

Filter:
- resonant filter sweep,
- LEVEL/DEPTH controls intensity or resonance/mix,
- TIME or beat position controls modulation behavior.

Flanger:
- short modulated delay,
- tempo-synchronized modulation,
- feedback protection.

Phaser:
- multiple all-pass stages,
- tempo-synchronized LFO,
- stable coefficients.

Pitch:
- real pitch-shifting behavior using a documented real-time-safe approach,
- not simple playback gain or a mislabeled filter,
- smooth transitions,
- bounded latency.

Slip Roll:
- capture and loop the selected recent segment,
- underlying live input continues advancing,
- when released, return to the current live position,
- avoid discontinuities.

Roll:
- capture and repeat a beat-sized segment,
- beat division controls loop length,
- controlled transitions on activation and release.

Vinyl Brake:
- simulate progressive platter slowdown,
- use a preallocated ring buffer and variable read rate or another documented technique,
- TIME determines braking duration,
- restore normal live operation safely.

Helix:
- create a looping, evolving delay/phase effect,
- distinctly different from Delay, Echo, Spiral, and Flanger,
- document its model.

Pan:
- automatic left/right movement,
- beat-synchronized LFO,
- equal-power or otherwise documented panning.

Do not implement effects as empty classes, simple gain changes, or aliases merely to satisfy the effect count.

Create .github/dependabot.yml for GitHub Actions updates.

GIT AND EXECUTION PROCESS

1. Inspect the existing repository before changing anything.
2. Preserve useful existing work.
3. Check for existing instructions and licenses.
4. Create or update documentation before major implementation where this clarifies the architecture.
5. Implement in coherent milestones.
6. Run all available formatting and tests after each major milestone.
7. Commit completed milestones with meaningful commit messages.
8. Do not amend or rewrite existing commits.
9. Do not create unnecessary branches.
10. Leave the worktree clean.
11. Never commit build outputs.
12. Never commit credentials.
13. Never commit generated release packages.
14. Never mark a test passed without evidence.
15. Never hide compiler errors by disabling an entire feature.
16. Fix root causes instead of commenting out failing tests.
17. Do not use empty catch blocks.
18. Do not leave TODO/FIXME markers for required functionality.
19. Do not replace required DSP with placeholders because the implementation is difficult.
20. Do not change public behavior merely to make a weak test pass.

GITHUB VALIDATION LOOP

If GitHub authentication and gh CLI are available:

1. Push committed changes.
2. Trigger or observe the GitHub Actions workflow.
3. Run:
   gh run list
4. Watch the relevant run:
   gh run watch <run-id> --exit-status
5. If a job fails:
   - inspect logs,
   - identify the actual cause,
   - correct the code or workflow,
   - commit the correction,
   - push,
   - watch the replacement run.
6. Repeat until Windows and macOS jobs pass.

If pushing or GitHub authentication is unavailable:

- do not pretend CI ran,
- commit all work,
- provide the exact commands the user must run,
- clearly state which validation remains pending.

FINAL VALIDATION REPORT

Create VALIDATION.md containing:

- commit hash,
- local commands run,
- local results,
- GitHub Actions run URLs or run IDs when available,
- Windows build result,
- macOS build result,
- test counts,
- artifact names,
- known limitations,
- hardware tests still required,
- licensing review still required,
- signing/notarization status.

DEFINITION OF DONE

The project is done only when all of the following are true:

- repository architecture is complete,
- the application target compiles on Windows through GitHub Actions,
- the application target compiles as a Universal macOS app through GitHub Actions,
- QuadBeatFXTests compiles on both systems,
- automated tests pass,
- all fifteen effects contain real functioning DSP,
- all UI controls are connected to functioning behavior,
- four mixer channels operate independently,
- EQ and Isolator modes work,
- automatic/manual/TAP BPM modes work,
- X-PAD and arrows work,
- effect frequency selection works,
- effect assignment works,
- TIME and LEVEL/DEPTH work,
- MIDI Learn works and persists,
- device mappings persist safely,
- packages are uploaded as GitHub Actions artifacts,
- tagged release workflow is present,
- reference image is excluded from distributions,
- documentation is complete,
- .gitignore is complete,
- no credentials or generated binaries are tracked,
- no required feature is represented only by a placeholder,
- VALIDATION.md accurately describes what was actually validated.

At completion, respond with:

1. concise implementation summary,
2. commit hashes,
3. GitHub Actions status,
4. artifact names,
5. test results,
6. hardware validations still required,
7. licensing/signing limitations,
8. any genuine unresolved issue.

Begin by inspecting the repository and creating a concrete implementation plan. Then execute the plan. Do not stop after presenting the plan.
